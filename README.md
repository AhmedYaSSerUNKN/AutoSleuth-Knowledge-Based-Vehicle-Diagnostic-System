AutoSleuth is a Streamlit application generated from a Jupyter notebook that implements a forward‑chaining inference engine with Certainty Factor (CF) reasoning and provides explainable diagnostics based on user‑supplied symptoms.

## Quick overview

AutoSleuth asks targeted diagnostic questions (organized by subsystem), accepts graded symptom inputs via sliders, evaluates a set of domain rules (73 rules across multiple subsystems), and returns ranked fault hypotheses with an explainable trace showing which rules fired and why.

This repository was created from the notebook `KBS_Code (1).ipynb`, which writes the Streamlit app (`app.py`).

## Features

- Clean Streamlit UI with dynamic, category‑based symptom questions.
- Forward‑chaining rule engine that computes evidence using min (AND) semantics.
- Per‑rule application factor and Certainty Factor arithmetic for combining multiple rules about the same fault.
- Explainability: a step‑by‑step trace of rule evaluation to help technicians understand the reasoning.
- Simple knowledge base structure (Python dict) — easy to extend and maintain.

## Quick start (local)

1. Clone the repository

```bash
git clone https://github.com/AhmedYaSSerUNKN/thinking_about_it.git
cd thinking_about_it
```

2. (Recommended) Create and activate a virtual environment

```bash
python -m venv .venv
source .venv/bin/activate   # macOS / Linux
.venv\Scripts\activate     # Windows PowerShell
```

3. Install dependencies

```bash
pip install -r requirements.txt || pip install streamlit
```

4. Ensure `app.py` exists. If not, open the notebook and re-run the cell that contains `%%writefile app.py`.

5. Run the Streamlit app

```bash
streamlit run app.py
```

6. Open your browser to `http://localhost:8501`.

## How it works (high level)

- Knowledge base: `QUESTIONS` is a dictionary mapping categories to symptom variables; each variable contains a UI label and a short rationale ("why ask this?").
- User input: every symptom is captured with a Streamlit slider (0.0–1.0) representing the presence/severity of the symptom.
- Evidence aggregation: for rules that require multiple conditions, the system uses evidence = min(condition_values) (AND semantics).
- Rule application: evidence is multiplied by a rule factor (default R = 0.7) to produce a per‑rule CF.
- CF combination: when multiple rules support the same fault, CFs are combined using CF_combined = CF1 + CF2*(1−CF1) to increase certainty.
- Output: faults are ranked by combined CF. The UI highlights the primary diagnosis, lists secondary suspects above a threshold, and provides a reasoning trace for transparency.

## Extending the knowledge base

- Add symptoms: update `QUESTIONS` in `app.py` with new category -> {var_key: (label, why_text)} entries.
- Add/modify rules: add `eval_rule(...)` lines in the rule block to define new logical relationships. Example format used in `app.py`:

```python
eval_rule(1, "Fuel Injector Suspect", apply_rule(evidence_cf(p['eng_light'], p['rpm_drop']), R), "IF Light + RPM Drop")
```

- Tune confidences: adjust the global `R` or add per‑rule factors to reflect domain confidence.
- Consider moving the KB and rules into JSON/YAML so non‑developers can edit them safely.
